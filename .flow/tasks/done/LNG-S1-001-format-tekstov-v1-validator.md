## Контекст / зачем
Песни и стихи автор пишет руками в JSON (`D-3`). Опечатка не должна молча терять перевод или ломать прогресс: приложение обязано сказать, где именно и что не так, на языке интерфейса. Валидатор — общий фундамент для загрузки в приложение и для проверки контента в репозитории.

## Цель
Доменная модель текста v1 и чистая функция проверки: на вход — содержимое файла, на выход — типизированный текст либо список ошибок и предупреждений с путём и локализованным сообщением (RU/EN/ES). Плюс ключ прогресса фразы.

## Объём
**Входит:**
- типы `TextDoc` (корень, строфа, строка, фраза, слово) по `content-format.md`;
- разбор JSON с позицией синтаксической ошибки (строка:столбец);
- проверка структуры (обязательные поля, типы, перечисления, незнакомые ключи вне `ext`) и межполевых правил 1–6, предупреждений 1–2;
- ключ прогресса фразы `phraseKey(textId, original)`;
- сообщения проблем — ключи i18n `texts.issue.*` в `ru/en/es`;
- проверка всего `content/texts/` (и `content/private/`, если он есть локально) в `npm run test`; сверка с JSON Schema на примерах.

**Не входит:**
- экран и поток загрузки файла, подтверждение замены по `id`, хранение — следующая строка BL-2;
- связывание слов с частотным словарём (BL-3);
- изменение самого формата (только исправление расхождений спеки и схемы, если найдутся).

## Критерии приёмки (AC-1…N)
- **AC-1.** Оба примера из `content/texts/` проходят проверку без ошибок и предупреждений.
- **AC-2.** Каждое правило-ошибка 1–6 из `content-format.md` даёт ошибку с путём в нотации `stanzas[0].lines[2].phrases[0]` и сообщением, понятным без чтения кода (цитирует проблемный текст). Файл с ошибкой не принимается.
- **AC-3.** Предупреждения 1–2 (строка без перевода, неполный набор переводов) выдаются, но текст принимается.
- **AC-4.** Битый JSON → одна ошибка с номером строки и столбца, а не исключение.
- **AC-5.** Сообщение любой проблемы есть на RU, EN и ES.
- **AC-6.** Ключ прогресса фразы не меняется от правки перевода, регистра, пробелов и пунктуации по краям и меняется от правки самого оригинала.
- **AC-7.** `npm run test` падает, если в `content/texts/` появился невалидный текст.

## Решения
- **D-1. Свой валидатор, а не ajv в рантайме.** Сообщения должны быть на языке интерфейса и называть строку/фразу по-человечески; у ajv — технические английские сообщения и +~120 КБ в бандл. JSON Schema остаётся контрактом для редактора (автодополнение через `$schema`) — расхождение ловит тест: ajv — только `devDependency`, примеры и негативные фикстуры прогоняются через оба.
- **D-2. Проблема = код + путь + параметры**, текст — из i18n в UI. Домен не знает языка интерфейса.
- **D-3. Вхождение фразы/слова в строку** — подстрока без учёта регистра после Unicode-нормализации NFC (иначе «ñ», набранная составным символом, «не найдётся»). Границы слова не проверяются — как в спецификации.
- **D-4. Путь — с нуля** (как в редакторе и jq); проблемный текст цитируется в сообщении, так что строка находится поиском.

## Подход
`app/src/features/texts/domain/`: `types.ts` → `issues.ts` (коды) → `parse.ts` (JSON + позиция) → `validate.ts` (структура, затем межполевые правила; структура сломана — межполевые для этого узла не проверяются, чтобы не плодить вторичные ошибки) → `phrase-key.ts`. `features/texts/issue-message.ts` — код → i18n. Тесты-вперёд по таблице ниже.

## Тесты
Класс риска: **К2** (валидация, ветвления) + **К1** для `phraseKey` (целостность прогресса) — property-based на инварианты.

| Вход | Ожидание |
|---|---|
| оба примера | 0 ошибок, 0 предупреждений |
| нет `id` / `kind: "film"` / ключ `titel` / `year: "1806"` | ошибка структуры с путём |
| строка без ключа оригинала | `missing_original` на строке |
| фраза только с оригиналом | `phrase_no_translation` |
| фраза/слово не входит в строку; входит в другом регистре; NFD-«ñ» | ошибка / ок / ок |
| `ref` на необъявленную или объявленную позже строфу; `lines`+`ref`; ни того ни другого | ошибка |
| два `id: "chorus"` | `duplicate_stanza_id` |
| `title` без ключа `lang` | `missing_original` на `title` |
| строка без перевода; строка без `en`, когда у остальных есть `en` | предупреждения, текст принят |
| битый JSON | `json_syntax` со строкой:столбцом |
| `ext` с любым содержимым | ок |
| `phraseKey`: регистр/края/повтор; другой оригинал | равны / различны (fast-check) |
| `content/texts/*.json` | валидны и по валидатору, и по ajv-схеме |

## Ключ к корректности / риски
Ключ фразы — это прогресс пользователя: нормализация должна быть стабильной (идемпотентной) и не схлопывать разные фразы. Межполевые проверки нельзя запускать на структурно битом узле — получится каскад бессмысленных ошибок.

## Итог реализации
**Сделано.** `app/src/features/texts/`: типы формата v1 (`domain/types.ts`), коды проблем (`domain/issues.ts`), разбор JSON со своим сканером позиции ошибки (`domain/parse.ts`; JavaScriptCore на iOS позиции в исключении не даёт), валидатор «структура узла → межполевые правила узла» (`domain/validate.ts`), ключ прогресса фразы (`domain/phrase-key.ts`), сообщения `texts.issue.*`/`texts.type.*` в `ru/en/es` и `issueMessage`. `content.spec.ts` проверяет весь `content/texts` (и `content/private`, если есть), соответствие имени файла `<id>.<lang>.json`, отсутствие `personal` в поставке и сверяет валидатор с JSON Schema через ajv (только devDependency, D-1).

**Проверка.** typecheck, lint, 105 тестов (из них 71 — фича), сборка. Покрытие `features/texts` — 92,7 % строк. Мутационная проверка: отключённые NFC-сравнение и предупреждение о неполных переводах ловятся тестами. Property-based (fast-check): идемпотентность `normalizePhrase`, независимость ключа от регистра и обрамления, несхлопывание разных фраз, сканер JSON на произвольном корректном JSON.

**Отклонения.** Спецификация уточнена под поведение: правило 0 (не JSON → строка:столбец), оригинал обязателен и в `title`, `ref` — только на строфу выше, вхождение без учёта формы записи Unicode, пути с нуля, состав нормализации ключа фразы.

**Грабли.** `new URL(\`…\`, import.meta.url)` в спеке Vite переписывает как ассет — путь через `node:path`. Попутно найдено и исправлено вне задачи: `taskctl` считал «топ-500»/«ES-15» из roadmap номерами задач (выдал LNG-S1-501) — счётчик теперь по префиксу проекта, с регресс-тестом в `~/.AI/tools/tests`.
